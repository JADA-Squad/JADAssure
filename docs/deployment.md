# Deploying JADAssure (DOC-002)

The pilot deploys to **Render** as one Docker web service plus a managed Postgres database,
defined in [`render.yaml`](../render.yaml). Every push to `main` rebuilds and redeploys the same
URL. Design: decision 0004.

```
GitHub main ──push──▶ Render build (root Dockerfile: React build + Python image)
                         │
                         ▼
               jadassure (web, $PORT)  ── API /api/*, React app /*, embedded worker thread
                         │
                         ▼
               jadassure-db (Render Postgres)
```

## First-time setup (owner, about 10 minutes)

1. Sign in at https://dashboard.render.com with GitHub.
2. Let the Render GitHub app access **JADA-Squad/JADAssure**. A JADA-Squad organization owner may
   need to approve this under GitHub → Organization settings → GitHub Apps.
3. **New → Blueprint** → select `JADA-Squad/JADAssure`, branch `main`. Render reads `render.yaml`
   and proposes `jadassure-db` and `jadassure`. Click **Apply**.
4. Wait for the first deploy (5–10 minutes). The service URL looks like
   `https://jadassure-xxxx.onrender.com`. `GET /api/health` should return `"status":"ok"`.
5. Sign in with a demo account, e.g. `financeanalyst@jm.com` or `admin@beyon.com`. The shared demo password is
   `DEMO_PASSWORD` in `backend/app/seed_demo.py`, which is visible only to people with repo access.

After that, every `git push` to `main` redeploys automatically (`autoDeploy: true`). Render shows
progress under **Events**, and a failed build keeps the previous version live.

## Configuration on Render

| Variable | Value | Why |
|---|---|---|
| `DATABASE_URL` | from `jadassure-db` | Render's `postgres://` URL is normalized to psycopg 3 by the app |
| `JWT_SECRET` | generated by Render | Never committed (GR-15). Rotating it signs everyone out |
| `EMBEDDED_WORKER` | `true` | Runs the job and schedule loop inside the web process |
| `SEED_DEMO_ON_START` | `true` | Creates the three synthetic DEMO orgs once (idempotent) |
| `SHOW_DEMO_ACCOUNTS` | `false` | Never list demo logins and passwords on a public URL (decision 0002 D-7) |
| `ALLOW_SIGNUP` | `false` | Strangers can't create organizations on the public URL |
| `ANTHROPIC_API_KEY` | unset | Claude stays unavailable (GR-08). Add as a secret only by decision |
| `OPENAI_API_KEY` | unset (secret, prompted by the Blueprint) | OpenAI stays unavailable. Set it in Render → Environment to use the assistant (decision 0010) |
| `OPENAI_MODEL` | `gpt-6.1-sol` | OpenAI model for every AI feature |

Change values in Render → service → **Environment**. Saving triggers a redeploy.

## Security requirements (NFR-06)

- **TLS in transit:** Render terminates HTTPS for `*.onrender.com` and custom domains with managed
  certificates. Plain HTTP redirects to HTTPS. Uvicorn runs with `--proxy-headers` behind Render's
  proxy. The connection between the service and Render Postgres stays on Render's private network.
- **Encryption at rest:** Render encrypts Postgres storage and backups at rest. For production,
  use a paid database plan with point-in-time recovery, and confirm the region meets the
  customer's data-residency needs (currently `frankfurt`).
- **Secrets management:** all secrets are environment variables managed by Render (generated
  `JWT_SECRET`, database credentials injected from the database resource). Nothing secret is in
  the repo or the image. Use Render's secret files or an external secrets manager if you add
  connector credentials.
- **Application controls already in place:** bcrypt passwords, expiring JWTs, a tenant-scoped data
  layer, a hash-chained audit log, formula-safe CSV exports, and no outbound write paths.

## Pilot limitations of the free plan (decision 0004 D-4)

| Limitation | Effect | Fix when needed |
|---|---|---|
| Free web instances sleep after ~15 min idle | First request takes ~1 min; scheduled check runs only happen while awake | Starter plan, or a separate worker service |
| Free Postgres expires after 30 days | Data is deleted after expiry | Upgrade `jadassure-db` to a paid plan before relying on it |
| No persistent disk | Uploaded CSV files and error-report files vanish on redeploy (imported **records** are in Postgres and survive) | S3-compatible `DocumentStore` adapter (deferred, decision 0001 D-4), or a Render disk on a paid plan |
| One process | API and worker share CPU | Split the worker into its own Render worker service (`python -m app.worker`) |

## Activating a real connector (when credentials exist)

1. Implement the connector against the protocol in `backend/app/domains/connectors/` (see its
   README) and register it.
2. Add the vendor's sandbox credentials in Render → **Environment** as secrets, e.g.
   `XERO_CLIENT_ID` / `XERO_CLIENT_SECRET`. Read them through `app/core/config.py`, never from
   the database.
3. Deploy (push to `main`). Then as admin: **Data setup** → create a connector source → **Sync now**.
4. Until then, only the clearly labelled demonstration connector is available (GR-14).

## Rolling back

Render → service → **Events** → choose an earlier successful deploy → **Rollback**. Database
migrations only add columns or tables so far, so older code runs against a newer schema. Re-check
this before any destructive migration.
